### Findings fixed

1. 🔴 **Marker SQL ordering** (`README.md`). The README said to run the marker "after merging T003". There is no window for that: every merge to `main` deploys to production, and the build now runs `pnpm payload migrate`. The README now says to run it **before** the PR merges, which is safe because the deployed code never migrates and Payload never pushes in production (`@payloadcms/drizzle` `connect`: push only when `NODE_ENV !== 'production'`). The SQL is now one transaction with an idempotent insert and a check query, and the migration name matches `src/migrations/index.ts` exactly (`20261006_141524_baseline`).
2. 🟡 **Failure mode undocumented** (`README.md`). Read `@payloadcms/drizzle/dist/migrate.js`: with a `batch = -1` row, `migrate` calls `prompts` (default No); No or cancel exits 0. Probes:
   - `batch = -1` present, stdin closed: `timeout 120 pnpm payload migrate </dev/null` → prompt printed, `exit=124` (hung). `review-batch-minus1-noninteractive.log`.
   - `-1` row deleted, no baseline row: `exit=1`, `type "enum_coming_soon_details_icon" already exists`, `payload_migrations` count 0, no table gained RLS (rolled back). `review-no-baseline-row.log`.
   - README now explains both, plus that pulled local databases (and so `pnpm preflight`) hit the same prompt until `pnpm db:pull` is re-run.
3. 🟡 **Baseline `down` dropped everything** (`src/migrations/20261006_141524_baseline.ts`), including `payload_migrations`, so `migrate:down` would destroy all data and then fail. It now throws: one-way, documented in a comment. Probe on a scratch copy: `pnpm payload migrate:down` → `Error migrating down 20261006_141524_baseline. Rolling back. … is one-way`; afterwards 15 tables remain and the baseline row stays. `review-baseline-down.log`.
4. 🟡 **Lint warnings introduced** (same file). `payload` and `req` unused in `up`/`down` (4 warnings; the report called all 11 pre-existing). Removed; `pnpm exec eslint src/migrations` → clean; lint total now 7 warnings, 0 errors.
